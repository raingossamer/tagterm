# TDD Skill — README

## 目的

本 Skill 定义的是一套 **通用的编程范式（universal programming paradigm）**：
Red → Read → Green → Refactor 的测试驱动开发流程。

> **核心理念**：方法论与编程语言无关。流程、原则、测试哲学跨任何技术栈通用；
> 代码示例只是用来"把抽象原则讲具体"的载体，可以随项目技术栈替换。

## 当前支持的编程语言（三语言）

配套文档中的代码示例目前覆盖以下三种栈，对应作者的常用技术栈：

| 层 | 语言 / 框架 | 测试工具 |
|----|------------|---------|
| 后端 | **Java** | JUnit5 + Mockito |
| 后端 / 脚本 | **Python** | pytest + unittest.mock |
| 前端 | **TS / Vue** | Vitest + Vue Test Utils |

每个概念都尽量同时给出三种语言的对照示例，读者可按当前项目所用语言各取所需。

## 文件分工

| 文件 | 是否含语言相关代码 | 说明 |
|------|:---:|------|
| `SKILL.md` | ❌ 语言中立 | TDD 主流程定义（RED→READ→GREEN→REFACTOR） |

## 如何切换 / 增减编程语言

因为方法论本身语言无关，切换栈时**只需改动 4 个配套文档**（`tests.md`、`mocking.md`、`interface-design.md`、`deep-modules.md`），`SKILL.md` 与 `refactoring.md` 永远不用动。

两种维护方式，按场景选择：

### 方式 A：多语言并列（当前做法）

一份文档里同时放多种语言的示例，读者各取所需。

- ✅ 适合：多栈混用、团队成员语言背景不同
- ⚠️ 代价：文档较长

### 方式 B：单语言主示例

只保留当前项目主力栈的示例，换项目时整体替换。

- ✅ 适合：单一技术栈项目，追求文档精简
- ⚠️ 代价：切换栈时要重写示例

### 切换步骤

1. 确定目标语言及其测试框架（如 Go + testing、C# + xUnit、Rust + cargo test 等）
2. 在 4 个配套文档中，按"原则不变、示例替换"的方式改写代码块
3. 保持每个示例的 **good vs bad 对照结构**，只换语言、不换要表达的原则
4. 文件名与 `SKILL.md` 中的链接引用保持一致（不要改文件名）

## 不变量（切换语言时务必保持）

无论用什么语言，以下原则恒定不变：

- 测试只验证**可观察行为**，不绑定内部实现
- 只在**系统边界** mock，不 mock 自己的模块
- 接口**接收依赖**而非内部创建；**返回结果**而非制造副作用
- 追求**深模块**：小接口 + 深实现
- 一次一个测试，垂直切片，禁止水平切片（先写全部测试再写全部实现）

> 这些不变量才是本 Skill 的本体；代码示例只是它们在某种语言下的一次投影。
